# Family Ledger — Full Project Audit

**Date:** 1 September 2026 · **Head:** `0233e4f` (main) · **Codebase:** ~13,000 LOC across 113 source files
**Scope:** full read of `src/`, `docs/`, `drizzle/`, `scripts/`, `.github/`, plus the complete 250-commit git history.

Every issue below marked **[verified]** was re-read and confirmed directly in the source while writing this
report, not taken on trust from the audit pass.

---

## 0. What the git history tells you

The repo is 14 days old (13 Aug → 26 Aug 2026), single-author (`Shreyas S S`), with three one-off
contributions (`Claude`, `qwen.ai[bot]`). Commits are clean, conventional, and atomic — genuinely
better hygiene than most projects this size. But the history reveals three structural problems:

1. **Velocity outran verification.** 250 commits in 14 days, ~30 of them on 24–25 Aug alone, each
   shipping a user-visible feature. Features were verified by the DB round-trip scripts, which are
   **skipped in CI whenever the `DATABASE_URL` secret is absent** (`.github/workflows/ci.yml:60`).
2. **The last four commits are an unwind.** `26588b2`, `cfb1627`, `ccc6a46`, `90dbd56`, `0233e4f` are
   all repairs to the 25 Aug hierarchy pass — including a **five-day window where production was
   serving stale code** while the DB had already migrated.
3. **The spec is frozen but the product is not.** `SPEC.md` is declared ❄️ FROZEN with 5 amendment
   passes recorded in `CHANGELOG.md`. The amendment log is excellent practice, but the frozen-spec +
   fast-shipping combination means `SPEC.md` now lags reality in places (see §1.7).

### Correcting the changelog's own process note

The 26 Aug addendum says *"nothing in the local check suite ran `next build`"* and recommends wiring a
build into CI. **CI already runs `next build`** — `.github/workflows/ci.yml:29`, on every push to main,
unconditionally. So the real gap is different and more serious:

> **`ci.yml` and `smoke.yml` do not gate anything.** Vercel deploys on push to `main` regardless of CI
> state. The build was failing loudly and correctly at `43a4289`; nobody was blocked by it, so
> production served the pre-hierarchy build for five days.

**Fix:** enable branch protection on `main` with `CI` as a required status check, or move deploys to
fire only from `workflow_run` on CI success. Do not add a second build step — add enforcement.

## 1. Issues

### 1.1 CRITICAL — Split mode writes amounts 100× too large **[verified]**

`src/components/transactions/transaction-edit-dialog.tsx:139-142` seeds the two split rows from
`paise`, but `splits[].amount` is a **rupee** string that `rupeesToPaise()` parses later
(`:125`, `:201`).

```ts
{ amount: Number(paise / 2).toString(), ... }        // paise/2 put into a RUPEE field
{ amount: (paise - Math.floor(paise / 2)).toString() }
```

A ₹100 row (10,000 paise) seeds both parts as `"5000"` → ` rupeesToPaise("5000")` = 500,000 paise
each. `splitTotal` = 1,000,000, `splitRemaining` = **−990,000**, so `canSplitSave` is `false` and the
UI reports the split as ₹9,900 over. **Split is unusable unless the user manually retypes both parts.**
Split shipped in `53e27d7` and has presumably never worked.

**Fix:** `String((paise / 2) / 100)` and `String((paise - Math.floor(paise / 2)) / 100)`.

### 1.2 CRITICAL — Trend chart Y-axis is off by 100× **[verified]**

`src/components/dashboard/charts.tsx:277` — `dataKey="expensePaise"` is paise, but the formatter
divides as though the value were rupees:

```tsx
tickFormatter={(v) => (Number(v) >= 100000 ? `${Number(v)/100000}L` : `${Number(v)/1000}k`)}
```

₹1,000 (100,000 paise) renders as **`1L`**. ₹50,000 renders as `50L`. The tooltip one line below
(`:278`) formats paise correctly, so **axis and tooltip visibly contradict each other** on the same
chart. Regression from the 6-month bar trend (`0062cc6`).

**Fix:** divide by 100 first — `v/100000` for `L` (i.e. `v/1e7`) and `v/1000` → `v/1e5` for `k`.

### 1.3 CRITICAL — Editing a row silently discards an inline-created category **[verified]**

`transaction-edit-dialog.tsx` keeps a local `cats` state synced from the server prop so categories
created inline appear immediately (`:92-96`). But the **save path reads the stale prop**:

| Line | Uses | Effect |
|---|---|---|
| `:297` | `categories.find(...)` | the value actually sent to `updateTransaction` |
| `:351` (`saveAsTemplate`), `:170` (split) | `cats.find(...)` | correct |
| `:573` (grid), `:634` (CTA label) | `cats` | correct |

So: create a category inline → the grid shows it selected → the sticky CTA reads
**"Save ₹1,250 · New Category"** → you tap it → `:297` can't find it in the server prop →
`categoryId` is written as `null`. **The expense silently becomes Uncategorized and the user is told
"Transaction updated".** The button lied about what it was about to do.

**Fix:** change `:297` to `cats.find(...)`.

### 1.4 CRITICAL — `db:migrate` is broken: migrations 0004 and 0005 collide **[verified]**

`drizzle/0004_wandering_templates.sql` creates `templates`, `templates_sort_order_idx` and
`transactions.reviewed_at`. `drizzle/0005_gorgeous_speed.sql` creates **all three again** — with bare
`CREATE TABLE "templates"`, `ADD COLUMN "reviewed_at"` and `CREATE INDEX "templates_sort_order_idx"`,
no `IF NOT EXISTS`.

Applying 0004 → 0005 fails on `relation "templates" already exists`. **The committed migration chain
cannot be replayed from scratch.** Production only works because everything is applied via
`db:push`, and CI's `db:migrate` step is silently skipped whenever the DB secret is unset — so
nobody noticed. 0005 also drops `NOT NULL` on `category_id` that 0004/0000 established, without
being labelled as the Amendment 20 change.

`0007` claims *"Idempotent; safe to re-run"* but its three `ALTER TABLE … ADD COLUMN` statements
(`:13-15`) have no `IF NOT EXISTS` — the claim is false. `0008` gets it right (`:18`).

**Fix:** rewrite 0005 to be idempotent (or squash 0004+0005), fix 0007, and make CI's migration step
non-skippable on a disposable Neon branch.

### 1.5 CRITICAL — Zero server-side authorization in every Server Action **[verified]**

`grep -rn "auth()" src/actions/ src/db/` → **no matches**. All five `"use server"` files
(`transactions.ts`, `settings.ts`, `member.ts`, `review.ts`, `templates.ts`) are gated *solely* by
`src/middleware.ts`.

Server Actions are separately addressable POST endpoints. Middleware alone is not defence in depth —
it has been bypassed before (CVE-2025-29927, `x-middleware-subrequest`), and the matcher here
(`:14`) is a complex negative lookahead that already excludes `api`, `manifest`, `icon`, `sw.js`,
`offline` and every static extension. One regex slip and `deleteTransactions` / `exportCsv` /
`updateMember` are public.

**Fix:** add `const session = await auth(); if (!session) return { ok: false, error: "Unauthorized" };`
as the first line of every exported action. Cheap, and it makes the actions self-contained.

### 1.6 HIGH — The Review queue's Delete button is a no-op **[verified]**

`review-queue-card.tsx:432-434` passes `onRequestDelete` a comment instead of a handler:
`/* handled by the row's own swipe affordance */`. The edit dialog renders the destructive button
(`transaction-edit-dialog.tsx:623-627`), calls the no-op, then closes. **Visible button, silent
no-effect, no toast** — the worst possible failure mode for a destructive control.

**Fix:** either hide `onRequestDelete` UI when no handler is supplied, or wire it to the queue's
delete-with-undo path.

### 1.7 HIGH — Dead interactive affordances

- **Category filter chip has an X that does nothing** — `filters.tsx:332-340` renders
  `<span className={cn(pill(true), …)}>` containing `<X/>` with no `onClick`. The group chip
  (`:313-325`) and every other chip in the bar is a real `<button>`. Looks clickable, isn't.
- **Empty state ignores `groupId`** — `transactions-list.tsx:408,413`: with only a group filter
  active, a filtered-to-empty ledger says "Nothing here yet / Log your first expense" instead of
  "No transactions found / Try clearing the filters".
- **`enableSelection` prop is never passed false** (`transactions-list.tsx:64`) — both call sites use
  the default, so the dashboard preview exposes bulk-select tooling it was explicitly opted out of
  (`369f1b8` "opt dashboard panel out").

### 1.8 HIGH — Security hardening gaps

| Issue | Location | Note |
|---|---|---|
| Non-constant-time password compare | `auth.config.ts:20` | `parsed.data.password !== master`. Use `timingSafeEqual`. |
| No rate limiting / lockout | `auth.config.ts:14-21` | A single shared password is brute-forceable with zero friction. |
| No session `maxAge` | `auth.config.ts:9` | 30-day JWT, no revocation path. |
| Cron endpoints outside the auth matcher | `middleware.ts:14` excludes `api` | `/api/cron/*` rely only on `CRON_SECRET`, compared with `!==` (`recurring/route.ts:27`, `telegram-digest/route.ts:9`). Fail closed when unset — good — but timing-unsafe and unthrottled. |
| `active_member_id` cookie | `member.ts:22-25` | Non-httpOnly is **deliberate and correct** per SPEC §3.2 (SSR determinism, no hydration flash). But it sets no `secure`, no `sameSite`, 1-year lifetime. Add `secure: true` in prod + `sameSite: "lax"`. |
| Attribution is untrustworthy | — | The member cookie is freely client-editable, so "who logged this expense" is advisory only. Worth stating in the UI rather than implying audit-grade attribution. |

### 1.9 HIGH — Polling and query cost

Two byte-identical hooks poll every 30 s **on every route including Settings**, each firing a server
action: `use-pending-review-count.ts:16` and `use-uncategorized-count.ts:19`. Both counts are *also*
recomputed server-side on every ledger render (`transactions/page.tsx:43-44`). The review predicate
(`review-where.ts:29-38`) is a sequential scan with a correlated `EXISTS` per row plus a 30-element
`IN` list, and there is **no index on `transactions.reviewed_at`**.

Also: `expandGroupFilter` re-queries group children up to 3× per request; `meta.ts:54-70`
`getRecentCategoryIds` does `MAX(created_at) GROUP BY category_id` over the whole table with no
supporting index; the dashboard 6-month trend has a lower date bound but **no upper bound**
(`(app)/page.tsx:93`), so one future-dated row widens the scan indefinitely.

**Fix:** merge the two hooks into one `/api/counts` call with a 60 s TTL and tab-visibility gating; add
`(reviewed_at) WHERE reviewed_at IS NULL` partial index; bound the trend window.

### 1.10 MEDIUM — Correctness and data integrity

- **Budget replacement is worse than documented.** `budget-mutations.ts:28-35` DELETEs the scope
  then INSERTs. With `month === null` it deletes **every** default budget before re-inserting — a
  failure leaves the scope empty, not "half-written" as SPEC §6.7 says.
- **`auto_day` change skips a month.** `templates.ts:75` leaves `lastAutoKey` untouched; the due test
  is `autoDay = day AND lastAutoKey <> monthKey` (`recurring/route.ts:50-52`). Change a template's day
  from 5 → 20 after the 5th already stamped and the bill never fires that month.
- **`?date=` override is shape-checked only** — `recurring/route.ts:33` accepts `2026-02-30`, which
  then fails on insert → 500.
- **Unescaped `LIKE` wildcards** — `query.ts:63` builds `ilike(note, "%term%")` from raw input, so
  `?q=%` matches everything. The dashboard deep-links notes into `?q=` (`(app)/page.tsx:269`).
- **Unbounded CSV export** — `transactions.ts:299-316`, no `LIMIT`, no streaming, whole result set
  concatenated in memory. `ORDER BY date ASC, created_at ASC` uses **unqualified** columns across two
  joins (breaks the day `categories` gains a `created_at`) and omits `time`/`id`, so tie order is
  nondeterministic.
- **`timestamp without time zone` cursor round-trip** — `schema.ts:70`, `query.ts:74-81`. Written by
  `now()` (server tz), read as JS `Date`, serialized via `toISOString()`, parsed back. Correct only on
  a UTC host.
- **Ledger summary ignores the exclude-bills toggle** — `query.ts:199` counts all spend while
  `budgets.ts:88` subtracts recurring. **The ledger total and the budget bar disagree.**
- **Slug-generation race** — `settings.ts:68-72`, `:116-120` read all slugs then insert; concurrent
  creates 500 on the unique constraint.
- **`ON DELETE NO ACTION` everywhere** — deleting a group would orphan its leaves; there's no group
  delete UI, and the cron's "member may have been deleted" fallback (`recurring/route.ts:59-61`) is
  unreachable dead code.
- **Test scripts mutate the live production DB.** `src/db/*-test.ts` load `.env.local` and
  write/delete rows in whatever database it points at. A `npm run test:hierarchy` run against prod
  credentials is one typo away from a bad afternoon.
- **No `try/catch` in any action**, and `row.id` is unguarded after insert (`transactions.ts:75`,
  `templates.ts:48`).

### 1.11 MEDIUM — The 2-level hierarchy left two gaps

- **Group-level budgets are impossible.** `budgets.categoryId` references `categories`, and groups

## 2. Feature suggestions and improvements to existing features

Ordered by value-per-effort for a 3-person household ledger.

### 2.1 Group-level budgets — highest value, closes a hierarchy gap

**(new)** Allow a budget row to target a **group**, rolling up its leaves. This is the single most
natural follow-on to the 25 Aug pass: the pie's unit of thought and the budget's unit of control
should match. Enforcement precedence: `leaf-with-own-budget` → `parent-group-budget` → `month default`
→ `every-month default`. Show a group budget as "Food & Provisions ₹12,400 / ₹10,000" with the
per-leaf split beneath it.

### 2.2 Per-expense shared ownership — fits the household model

**(new)** The ledger tracks *who spent* (`member_id`) but not *who benefits*. For a family with a
kid, most spend is shared. Add an optional `split_with` (member ids) or a simple
`shared: boolean` that lets the dashboard compute **per-person attributable spend** — "Dad ₹18k,
Mom ₹9k, Household ₹24k". This is the "Who spent" card that was dropped in `17fec2a`, but done
properly: as an attribution view rather than a filter.

### 2.3 Fix and extend Split

**(improvement)** Fix §1.1, then make it useful: split unevenly (%) or by amount, allow different
categories per part (already supported in the data model), and show a live "₹X remaining to
allocate" counter. Split currently has no reason to exist for a single payment of one category.

### 2.4 Recurring detection, not just recurring templates

**(new)** Templates require the user to know a bill repeats. Most households don't declare this.
Mine the last 6 months for stable `(amount ±5%, note-similarity, ~30-day cadence)` clusters and
surface: *"Looks like ₹2,499 to Airtel repeats monthly — create a template?"* One tap to confirm.
This converts the ledger's history into the template list instead of asking the user to maintain it.

### 2.5 Budget pacing should be the dashboard's headline

**(improvement)** The pacing line shipped in `b213994` and `478e57f`, but budgets still read as
"₹12,400 / ₹10,000 = over". Reframe as **"₹1,850 left for 11 more days (₹168/day)"**. That is the
number that changes behaviour. Add a projected month-end figure: *"at this rate you'll land at
₹14,200"*.

### 2.6 Rollover and envelope semantics

**(new)** Currently every month resets. Add optional rollover: unspent category budget carries into
next month (or is clawed back). This is how households actually behave with irregular categories like
vehicle maintenance, where a ₹500/month limit is meaningless but ₹6,000/year is right.

### 2.7 Search becomes a real query tool

**(improvement)** Today `?q=` is a substring note match with `pg_trgm` (`f65e4c8`), and the wildcard
leak (§1.10) means `%` is unusable. Add: amount range (`amount_min`/`amount_max`), multi-term AND
search, member+category+tag+range combinations that persist as shareable URLs, and **saved searches**
("Big fuel spends", "Kid stuff last quarter"). Escape `LIKE` metacharacters on the way in.

### 2.8 Anomaly and insight layer

**(new)** The dashboard is descriptive; make it diagnostic. Cheap, high-signal checks:
- "Fuel is 40% above your 6-month average this month"
- "3 uncategorized entries worth ₹4,200" (existing, but promote to the top)
- "Your largest ever single spend in Dining Out was ₹3,100 — today's ₹2,900 is close"
- Month-over-month category deltas exist (`b213994`) but only on the dashboard; surface them in the
  ledger per-day headers too.

### 2.9 Receipts and attachments

**(new)** Blob storage (Vercel Blob) + a photo field on transactions. For a family ledger this is the
difference between "I trust this number" and "I'll re-enter it later". Even without OCR, a photo
attached at capture time makes month-end reconciliation trivial. OCR-lite (read the printed total)
would be a strong follow-on.

### 2.10 Export and backup

**(improvement)** CSV is unbounded (§1.10) and 7-column. Add: streaming export, JSON (full fidelity,
including `reviewed_at` and attachments), XLSX for spreadsheet users, and a **scheduled monthly
email/Telegram of the CSV** — the Telegram digest foundation already exists (`c7c1fb6`). Also an
import path so a restore is possible; right now export is one-way.

### 2.11 Notifications

**(new)** The budget-alert logic exists server-side (`budget-alert.ts`) but only surfaces as a toast
after you happen to open the app. With the PWA already installable, Web Push for "80% of your Food
budget, 8 days left" and "3 bills un-reviewed" is the natural next step.

### 2.12 Miscellaneous improvements

- **Undo → full history.** The 5 s undo toast is good. Add a persistent audit trail
  (`activity_log`): who changed what, when, with restore. Given the member cookie is editable (§1.8)
  this is the only trustworthy attribution available.
- **Templates: pause, skip, and variable amounts.** `auto_day` exists but there's no "skip this
  month" or "amount varies — ask me".
- **Category merge.** Rename exists; merging two leaves (and re-pointing history) is the missing
  operation and the usual reason taxonomies rot.
- **Multi-month compare view.** 6-month trend exists as bars; a category × month matrix would answer
  "is fuel creeping up?" directly.

## 3. UI/UX improvements

Each subsection below ends with a **Decision — to be implemented** line recording the approach
agreed on 2026-09-03. Where an item has only one correct answer, it is fixed directly rather than
presented as a choice.

### 3.1 Fix the three lying affordances (§1.3, §1.6, §1.7)

A button that lies is worse than no button. Specifically: make the edit dialog's CTA label and its
save payload read from the same source; remove or wire the Review delete; make the category chip a
real button.

**Decision — to be implemented:** Repair each affordance rather than removing it. The category chip
becomes a real `button` that opens the category picker. The Review queue Delete is wired through the
same delete-and-undo path as transactions. The edit dialog's CTA label and its save payload both
derive from one dirty-field count, so the label can never claim more or less than it actually sends.
Chosen over deleting the controls (loses the quick category switch) and over a labels-only fix
(buttons would still do nothing).

### 3.2 Stop closing dialogs before the server answers

`transaction-edit-dialog.tsx:322-323` applies the optimistic row and closes *immediately*; on failure
it emits the original row back and toasts — but the sheet is already gone, so the user loses their
edits and sees only "Could not save". Combined with §1.3, a failed edit is unrecoverable.
**Keep the sheet open on failure**, or reopen pre-filled with the attempted values. Relatedly, the
`row.id !== lastKey` re-init guard (`:100-117`) means closing and reopening the *same* row leaves
stale values.

**Decision — to be implemented:** Keep the sheet open and show the save state. The optimistic row
still applies immediately, but the sheet stays open with a saving state, closes on success, and on
failure stays open with an inline field-level error — so a failed edit is never lost. The re-init
guard is also fixed so reopening the same row re-reads current values instead of showing stale ones.
Chosen over a pessimistic save (makes every save feel slow) and over close-then-reopen-prefilled
(the flash is jarring).

### 3.3 Delete-undo has a data-loss window **[verified pattern]**

`transactions-list.tsx:212-218` uses Sonner's `onAutoClose` to commit the queued delete. Sonner fires
`onAutoClose` **only on timer expiry** — swiping or dismissing the toast skips it. The pending delete
then survives in `pendingRef` and is only flushed on unmount (`:99-109`). Kill the app in that window
and the delete is silently lost. Use `onDismiss` as well, or make the flush explicit.

**Decision — to be implemented:** Make the flush explicit. Commit the queued delete on `onDismiss`
as well as `onAutoClose`, and flush any remaining pending deletes on route change — not only on
unmount. Keeps the optimistic feel with no silent data loss. Chosen over delete-immediately-plus-
re-insert (needs a restore payload and loses row position) and over a confirm dialog (adds friction
to every single delete).

### 3.4 Accessibility — the app is visually rich and screen-reader invisible

Highest-impact fixes, roughly in order:

1. **All three sheets are unnamed dialogs** — `quick-add-sheet.tsx:320`,
   `transaction-edit-dialog.tsx:381`, `category-picker-sheet.tsx:56` render `SheetContent` with
   `showCloseButton={false}` and **no `SheetTitle`**. Radix warns in console; screen readers announce
   a nameless dialog. Add a visually-hidden `SheetTitle` + `aria-describedby`, and an initial focus
   target for the two sheets that lack one.
2. **Hidden delete button is keyboard-focusable** — `transaction-item.tsx:132-139` places a
   destructive button behind *every* row, in the tab order even when not swiped open. Keyboard users
   tab onto an invisible delete. Needs `tabIndex={swiped ? 0 : -1}` + `aria-hidden`.
3. **No text alternative for any chart** — `charts.tsx:168-179`, `:271-281`. The entire spend
   breakdown is unavailable to SR users. Add `role="img"` + `aria-label` summarising, plus the legend
   data is already in the DOM as a list — mark it up as the accessible equivalent.
4. **Tag radiogroup isn't keyboard-navigable** — `transaction-fields.tsx:180-206`: `role="radiogroup"`
   with no arrow-key handler, and the checked radio is `tabIndex={-1}` while unchecked ones are
   tabbable — roving tabindex inverted.
5. **No `aria-current` on bottom nav** (`bottom-nav.tsx:68-90`); active state is colour-only. `<nav>`
   has no `aria-label`.
6. **Unlabelled search input** (`filters.tsx:157-163`, placeholder only).
7. **Errors not announced** — `login-form.tsx:49`, `budget-card.tsx:452`, `quick-add-sheet.tsx:452`
   lack `role="alert"`/`aria-live`.
8. **Touch targets under 44px** in at least 6 places: `budget-card.tsx:130`,
   `transaction-fields.tsx:394-399`, `categories-manager.tsx:310-333`, `members-manager.tsx:88-95`,
   `transactions-list.tsx:465-471`, month-strip chips.

**Decision — to be implemented:** All eight get fixed. Three involve a real choice:

- **(1) Sheets** get a visually-hidden `SheetTitle` + `aria-describedby`, plus an initial focus
  target on the two sheets that lack one. Chosen over a bare `aria-label` (gives no description, no
  focus target) and over a visible heading (would restyle all three sheets).
- **(2) Swipe-revealed delete** is gated with `tabIndex={swiped ? 0 : -1}` + `aria-hidden`, so it
  leaves the tab order until revealed. Chosen over conditionally rendering it (pops in rather than
  sliding with the row) and over `inert` (needs a polyfill on older Safari).
- **(3) Charts** get `role="img"` with a one-sentence `aria-label` summary, and the legend already in
  the DOM is promoted to a properly labelled list. Chosen over an offscreen data table (duplicates
  the data, can drift) and over a visible expandable table (adds UI to an already dense dashboard).

The remaining five have one correct answer and are fixed directly: tag radiogroup gets arrow-key
handling with the roving tabindex un-inverted; bottom nav gets `aria-current` and the `<nav>` an
`aria-label`; the search input gets a real label; the three error sites get
`role="alert"`/`aria-live`; touch targets are raised to a 44px minimum in all six places.

### 3.5 Mobile and PWA

- **The service worker can never update.** `service-worker-register.tsx:9-24` registers once on
  `load` and never calls `registration.update()` or listens for `updatefound`. `sw.js` is pinned at
  `VERSION = "v1"` forever — every future deploy is served from a stale cache until the user clears
  site data. This is the highest-risk PWA issue.
- **Offline sync fails silently.** `offline-sync.tsx:33-48`: a non-network rejection `break`s without
  setting `blocked`, so a permanently-failing entry re-queues with no user-visible error. Also
  `runSync` fires on every window `focus` with an IndexedDB read each time.
- **Toast offsets are hardcoded guesses.** `sonner.tsx:19` uses `4rem` against a `h-14` (3.5rem)
  header; `transactions-list.tsx:460` and `review-queue-card.tsx:398` hardcode `4.5rem` for nav
  height. Introduce a `--bottom-nav-h` / `--header-h` token pair.
- **Manifest**: a single 512×512 `/icon` declared twice, no 192px PNG; `theme_color` is dark-only
  (`#171717`) while `layout.tsx:37-40` declares both. No iOS install affordance —
  `install-button.tsx:40` renders nothing on Safari, where the app is most likely to be installed.
- `appleWebApp.statusBarStyle: "black-translucent"` (`layout.tsx:25`) with no top safe-area padding.

**Decision — to be implemented:**

- **Service worker** gets a cache version bumped per deploy, an `updatefound` listener, and a
  dismissible "New version available — tap to refresh" bar. Chosen over auto-reload (risks
  reloading mid-expense) and over a silent periodic check (user may wait a day to see a fix). This
  is the highest-risk item in Section 3.
- **Offline sync** sets `blocked` on any non-network failure and surfaces a persistent
  "N entries need attention" badge with a retry action, instead of re-queuing silently. Chosen over
  backoff-only (a permanent failure still needs a visible state) and over a bare pending-count
  indicator (doesn't explain *why* an entry is stuck).
- **Toast offsets** move to a `--bottom-nav-h` / `--header-h` token pair.
- **Manifest** gains a 192px PNG, a per-scheme `theme_color`, and an iOS install affordance;
  `black-translucent` gets matching top safe-area padding. These are mechanical.

### 3.6 Mobile interaction polish

- **Row swipe sets state on every `touchmove`** (`transaction-item.tsx:88-91`) — unthrottled, and no
  `onTouchCancel`, so an interrupted touch leaves a row stuck open. The long-press guard (`:68`)
  closes over a stale `dx`.
- **Month strip hijacks scroll on mount** — `month-strip.tsx:36` fires `scrollIntoView({behavior:
  "smooth"})` on every mount, yanking the page.
- **Skeleton heights are hardcoded** (`loading.tsx:33`, `h-[340px]` for the pie) and don't match the
  variable-height cards they replace → layout shift on handoff, defeating the point of
  `78421fc`.

**Decision — to be implemented:** Keep the swipe gesture but make it robust — coalesce `touchmove`
into a single animation frame, add an `onTouchCancel` handler that snaps the row shut, and read the
drag distance from a ref so the long-press guard stops closing over a stale `dx`. Chosen over
migrating to pointer events (a rewrite of the swipe component) and over replacing the gesture with
an overflow menu (loses fast swipe-to-delete). The month strip stops calling `scrollIntoView` on
mount — it scrolls only on a real month change, and instantly rather than smooth. Skeleton heights
follow the variable-height cards they replace instead of a hardcoded `h-[340px]`.

### 3.7 Consistency and design tokens

- **Hardcoded hex colours bypass the token system** in at least 8 places: `page.tsx:148-150`
  (`#0ea5e9`/`#8b5cf6`/`#f59e0b`), `page.tsx:301`, `charts.tsx:279` (`#ef4444`), `budget-bar.tsx:72`,
  `transaction-item.tsx:175,200`, `bottom-nav.tsx:84`. Meanwhile `--chart-1..5` are defined in
  `globals.css:70-74` and **never used**. Dark mode will drift.
- **Duplicated UI blocks** — the bulk-action bar is near-verbatim in `transactions-list.tsx:459-494`
  and `review-queue-card.tsx:397-412`; the member dropdown appears three times
  (`member-switcher.tsx:52-71`, `quick-add-sheet.tsx:332-358`, `transaction-edit-dialog.tsx:407-432`);
  the `<optgroup>` builder twice; Esc-to-exit + selection-mode effects twice.
- **Mixed component patterns** — shadcn `Select` in `filters.tsx` vs raw `<select>` in
  `templates-manager.tsx:175` and `transaction-edit-dialog.tsx:484`. `Button size="sm"` is overridden
  to `h-9` in ~15 places because the base is `h-7`; `size="xs"` is used exactly once.
- **Inconsistent copy** — "No transactions found" / "Nothing here yet" / "No items pending review ✓" /
  "Nothing waiting —"; pluralisation helpers differ between the two list surfaces.

**Decision — to be implemented:**

- **Colours:** adopt the tokens that already exist — map every hardcoded hex onto the unused
  `--chart-1..5` set and delete the literals, so dark mode inherits correct values instead of
  drifting. Chosen over adding semantic tokens (larger set to maintain) and over a lint-rule-only
  fix (never repairs the existing drift).
- **Button sizing:** fix the base `Button size="sm"` to `h-9` and delete the ~15 `h-9` overrides,
  retiring the single-use `size="xs"`. One source of truth for control height.
- **Duplication:** extract the shared blocks into components — the bulk-action bar, the member
  dropdown (3 copies), the `<optgroup>` builder, and the Esc-to-exit + selection-mode effects.
- **Copy:** standardise the four empty-state strings and the two pluralisation helpers on one
  helper each.

### 3.8 Performance / first paint

- **The dashboard bundles the entire ledger editor.** `(app)/page.tsx:19` → `TransactionsList` →
  `CategoryPickerSheet` + `TransactionEditDialog` + Recharts, all on first paint; `QuickAddSheet` is
  mounted on every route from `layout.tsx:42`. The dashboard is the first thing a user sees and it
  ships the editing stack. Lazy-load the edit dialog and category picker on first open.
- **Two permanent 30 s pollers** mounted from `BottomNav` on every route (see §1.9).
- `budget-manager.tsx:102-112` effect deps include `leaves`, recreated every render → body runs
  every render.

**Decision — to be implemented:** Lazy-load `TransactionEditDialog` and `CategoryPickerSheet` on
first open, keeping the transaction list eager. Chosen over splitting the ledger onto its own route
(changes navigation users are used to) and over swapping the chart library (the editor is the larger
share of the bundle). The two permanent 30 s pollers are replaced with shared, visibility-aware
polling that stops when the tab is hidden. `budget-manager.tsx` effect deps are fixed so `leaves`
does not recreate the body on every render.

Worth saying, because audits usually don't: the keyset pagination is correct and genuinely
well-implemented, the money boundary (integer paise, NUMERIC(12,2) at rest) is disciplined, the
IST timezone handling is deliberate and consistent, the server actions are Zod-validated at the
boundary with parameterised SQL throughout (**no injection found**), the optimistic-update + 5 s undo
pattern is the right call for this app, and the SPEC/CHANGELOG amendment discipline is better than
most teams manage. The problems above are mostly the predictable result of shipping 250 commits in
14 days without a gate — not of careless engineering.
