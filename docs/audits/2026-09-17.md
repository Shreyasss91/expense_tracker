# Family Ledger — Project Audit

**Date:** 17 September 2026
**Audited commit:** f117568
**Scope:** Source review, local validation, and npm dependency advisory checks. No source files were changed or committed during the audit.

The main risks are dependency security, a broken service worker, and transaction duplication or loss.

## 1. Critical — Production dependency advisories

**Location:** package.json:45

The successful production-only npm audit --omit=dev reports **7 vulnerabilities: 1 critical, 4 high, and 2 moderate**. Next.js is flagged for remote-code-execution advisories involving Windows hosting and AVIF image optimization:

- https://github.com/advisories/GHSA-p293-qw3h-jr36
- https://github.com/advisories/GHSA-2xp9-vwfh-vxw4

This verifies an affected dependency tree, not exploitability of the deployment. Production dependency findings also cover fast-uri, hono, js-yaml, postcss, qs, and sharp. Package inclusion does not itself establish runtime reachability.

**Recommendation:** Update Next.js and affected transitive dependencies, review the lockfile changes, and rerun validation. Avoid blindly using npm audit fix --force: the full audit proposes a breaking Drizzle Kit downgrade. Advisory results reflect the registry response at audit time.

## 2. High — Service worker cannot parse

**Locations:** public/sw.js:123 and public/sw.js:135

The publicly served JavaScript contains TypeScript assertions (as string and as WindowClient). **Confirmed:** node --check public/sw.js fails with SyntaxError: Unexpected identifier 'as'.

New service-worker registrations fail, preventing its offline caching and push handling; existing users may retain an older worker. Browser registration was not separately tested.

**Recommendation:** Remove the assertions and add a JavaScript syntax check to CI. The normal lint, typecheck, and production build did not catch this failure.

## 3. High — Offline saves can silently disappear

**Locations:** src/lib/offline-queue.ts:60 and src/components/quick-add/quick-add-sheet.tsx:273

IndexedDB failures resolve as null, but enqueue returns no success status. Quick Add nevertheless clears the form and announces “Saved offline.” Request success also precedes transaction completion, so a later abort is missed.

**Recommendation:** Wait for transaction completion, propagate failures, and retain the form until persistence succeeds.

**Evidence:** Source review; storage-failure scenarios were not executed in a browser.

## 4. High — Offline retries can duplicate expenses

**Locations:** src/components/pwa/offline-sync.tsx:43 and src/actions/transactions.ts:63

Sync sends only the payload, ignoring its stable clientId; the server generates a fresh UUID every time. A lost response after a successful insert leaves the queued item available for another insertion. Multiple tabs can also replay it.

**Recommendation:** Use a stable, server-enforced idempotency key.

**Evidence:** Source review; concurrent or interrupted database writes were not executed.

## 5. High — Successful inserts can be reported as failures

**Location:** src/actions/transactions.ts:89

Budget-alert calculation runs after insertion inside the same error handler. If that query fails, the action reports “Could not save” although the expense exists. A retry can duplicate it.

**Recommendation:** Separate mutation success from optional alert computation.

**Evidence:** Source review; post-insert database failure was not injected.

## 6. Medium — Recurring entries are not atomically deduplicated

**Location:** src/app/api/cron/recurring/route.ts:100

Insertion and lastAutoKey updates are separate operations. Concurrent executions or a failure between them can create duplicate monthly expenses.

**Recommendation:** Enforce unique template/month identity at the database write boundary.

**Evidence:** Source review; concurrent cron execution was not tested.

## 7. Medium — CSV restore can omit legitimate duplicates

**Location:** src/lib/import-apply.ts:119

Existing canonical CSV identities are stored in a Set, losing occurrence counts. If two identical expenses belong in the backup but only one remains in the database, restore considers both present and does not recover the missing occurrence.

**Recommendation:** Use occurrence-aware matching; prefer ID-preserving backups for reliable restoration.

**Evidence:** Source review; database-backed restore scenarios were not executed. Passing serializer/parser tests do not validate this database-resolution behavior.

## Limitations

- No live deployment or browser registration testing was performed.
- No database-backed mutation scenarios or actual migration replay were run. Journal consistency is not proof that the migration chain applies successfully.
- Dependency exploitability was not tested.
- Source-review findings are not claims that the corresponding failure has already occurred in production.

## Recommended Order

1. Remediate affected dependencies.
2. Repair the service worker and add its syntax check to CI.
3. Make transaction writes durable and idempotent, including offline replay and recurring entries.
4. Correct occurrence-aware CSV restoration and add database-backed regression coverage.
